# How the claude-sandbox persistence layer works

> This file is a global read-only skill, regenerated by `claude-sandbox create` on every run. You cannot edit it from inside the sandbox, and local edits would be overwritten anyway. To customise, copy the directory to a different name (e.g. `claude-sandbox.local/`) under a *local* skills dir.

You are running inside an Incus container managed by `claude-sandbox`. The container is disposable: `claude-sandbox destroy create` wipes its OS, packages, and everything under `$HOME` that isn't one of the mounts below. That narrowness is deliberate — it is what keeps one project's sandbox from silently changing another's. Six things survive a rebuild:

1. **The mounted project directory** — same path on host and sandbox, read-write. Commits, build artefacts, and files you drop in the tree persist on the host.
2. **Local skills** — `~/.claude/skills/`, read-write, **this project only** (host: `/test/config/skills/-test-project/`). Skills you author land here.
3. **Local memory** — `~/.claude/projects/-test-project/memory/`, read-write, **this project only** (host: `/test/config/memory/-test-project/`). `MEMORY.md` is the always-loaded index. `<slug>` is the project realpath with `/` replaced by `-`, matching Claude Code's own convention.
4. **Global skills** — **read-only**, shared by *every* sandbox. They appear as extra entries alongside your local ones in `~/.claude/skills/`, but you cannot edit them from here (host: `/test/config/skills-global/`).
5. **Global memory** — `~/.claude/global-memory/`, **read-only**, shared by every sandbox; always-on rules and facts. Its `MEMORY.md` is auto-injected into context at session start by a `SessionStart` hook (and pointed at by the CLAUDE.md stub as a backstop), so it reaches you without a manual read (host: `/test/config/memory-global/`).
6. **Global output styles** — `~/.claude/output-styles/`, **read-only**, shared by every sandbox (host: `/test/config/output-styles/`). `create` seeds a managed `ste100.md` (a concision-first style) and names the active style in `~/.claude/settings.json`. There is no local tier: a style is a standing register for how you write, not project knowledge, so you neither author nor edit one. If the user wants it changed, the change is theirs to make host-side, in `/test/config/output-styles/` or via `SANDBOX_OUTPUT_STYLE` in the config.

Everything else under `~/.claude/projects/-test-project/` (sessions, todos) is ephemeral — per-conversation state, not knowledge to carry forward. The container OS (`/etc`, `/usr`, `/var`, installed packages, systemd units other than the reporter) is wiped on `destroy`.

## Why your world is this narrow

The isolation is the design, not a bug. You write only to the two **local** tiers, and local means *this project's host path only*. A skill you draft or a fact you learn here is invisible to every other project's sandbox. The three **global** tiers are the only things that cross projects, and inside the sandbox they are read-only. So nothing you do can widen its own blast radius — you cannot make a change that silently reaches the user's other work. That is the guarantee the tiers buy.

## Promotion: how something becomes global

You cannot promote anything yourself. Promotion is a host-side move by the user: they move the skill dir or memory file from a local tier into the matching global tier —

- skill: `/test/config/skills/-test-project/<name>/` → `/test/config/skills-global/<name>/`
- memory: `/test/config/memory/-test-project/<file>` → `/test/config/memory-global/<file>`

Then it re-mounts read-only into every sandbox on the next `create`. So the right move when you believe something should be global is: **write it to the local tier, then tell the user it's a promotion candidate and let them decide.**

## Skills vs. memory — which to use

Use a **skill** when the content is a *procedure or recipe* and you can write a precise `description` naming the trigger ("how to set up an Incus VM", "how to debug systemd unit failures"). Skills are lazy-loaded by description match — they cost nothing when irrelevant.

Use **memory** when the content is a *fact about the user, project, or domain* ("user is a senior Go dev", "release freeze starts 2026-03-05", "auth rewrite is driven by legal"). `MEMORY.md` is always loaded — keep it terse.

Rough rule of thumb: "how to…" → skill; "X is…" or "we decided…" → memory. Cuts across the other axis: "does this apply to just this project or everywhere?" decides local vs. global — but you only ever *write* local; global is the user's promotion.

## Authoring a skill

Create it under your local skills dir, `~/.claude/skills/<kebab-name>/SKILL.md`:

```markdown
---
name: <kebab-name>
description: <one sentence describing exactly when this skill should fire — be specific; vague descriptions never match>
---

# <human-readable title>

<body — loaded into context only when the description matches>
```

The `description` field is the entire gate. "How to do X in environment Y" beats "X helpers". A vague description never loads.

## Authoring memory

Follow the auto-memory rules in the main system prompt. Local memory files land in `~/.claude/projects/-test-project/memory/` (host: `/test/config/memory/-test-project/`). `MEMORY.md` is the always-loaded index; topic files are pointed to from it. Keep index lines under ~150 chars — past 200 they get truncated. Global memory (read-only here) works the same way but its index lives in `~/.claude/global-memory/MEMORY.md`.

## When something doesn't persist

If a file is gone after `destroy create`, it was outside the six layers above:

- Files under `~/.claude/projects/-test-project/` outside `memory/` — sessions and todos go away on purpose.
- `~/.claude/settings.json`, `~/.claude/hooks/`, `~/.claude/CLAUDE.md`, and `~/.claude/CLAUDE.d/` — not just ephemeral but *regenerated* by every `create`. So a theme change, an output style picked with `/output-style`, or an edit to a CLAUDE.d note is reset on the next rebuild. Those are the user's settings to change host-side, in the config or in `bin/claude-sandbox`.
- A write into a **global** tier — it's read-only inside the sandbox; the write either failed or landed in an ephemeral overlay. Author locally instead.
- Anything under `/etc`, `/usr`, `/opt`, `/var` — container OS, ephemeral.
- Files in `$HOME` outside the mounted dirs — ephemeral.
- Packages installed with `apt` / `pip` / `npm -g` — ephemeral. To survive, bake them into the base image (see `build_base_image` in `bin/claude-sandbox`) or install per-project under the mounted project tree.

## Host-side layout (for the user)

- Local skills:  `/test/config/skills/-test-project/`
- Global skills: `/test/config/skills-global/`
- Local memory:  `/test/config/memory/-test-project/`
- Global memory: `/test/config/memory-global/`
- Output styles: `/test/config/output-styles/` (global only)

The user edits, prunes, and promotes these directly between sandbox lifecycles — they're just files on the host. `claude-sandbox full-destroy` deletes the container *and* wipes this project's **local** skills and memory (`/test/config/skills/-test-project/` and `/test/config/memory/-test-project/`); the shared global tiers are never touched. Plain `destroy` leaves everything intact.
